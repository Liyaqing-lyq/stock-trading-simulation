## 3. PR 流程（规格第 11 节强制要求）

### 3.1 硬性规则
1. 任何代码变更（无论人写还是 AI 生成）都必须通过 Pull Request 合入主分支，且至少一名队友 review 后才能 merge；
2. AI 生成的代码/算法/测试必须在 PR 描述中显式标注 `[AI-Generated]`；
3. review 不是走过场：必须对线程安全、异常处理、撮合逻辑正确性留下实质评论；
4. 最终文档需附仓库链接与已关闭 PR 讨论，演示时会被抽查。

### 3.2 本地开发与正式合入

先核对当前分支、远端和队友已有提交，再在功能分支工作；Codex 新分支默认使用 `codex/` 前缀。只提交本任务改动，保留用户和队友未提交的内容。

开发 → 本地验证 → 推送功能分支 → 创建带 `[AI-Generated]` 标注的 PR → 至少一名人工成员实质 review → 处理反馈、通过检查 → 合入。远端暂不可用时可保存本地提交和审阅草案，但等待补齐 PR 与人工 review 后才能正式合入。

本地 `--no-ff` 提交、写一个 reviewer 名字或 AI 的独立审查，都不能代替课程要求的人类 review。旧版本“先本地合主干、再补 PR”的示例撤销。真实评审链接和讨论摘要可保存在 `docs/pr-reviews/`，不能编造讨论记录。

### 3.3 PR 描述模板（可直接复制）

```markdown
## 变更内容
- 一句话说明本 PR 做了什么

## 关联评分项
- [ ] 核心：撮合 / 多标的 / 账户 / GUI / CSV / 异常校验
- [ ] 进阶：多线程 / 市价单 / LLM / 撤单

## AI 参与标注
- [AI-Generated] 哪些文件/方法由 AI 生成或大幅改写（必填，没有则写“无”）

## 线程安全说明
- 共享状态、加锁范围、锁顺序；是否有锁外副作用

## 验证证据
- `mvnw.cmd test` 结果（Tests run / Failures / Errors）
- 手工验证步骤与真实输出片段

## Reviewer 检查点
- [ ] 撮合是否可能出现订单簿交叉（bestBid ≥ bestAsk）
- [ ] 冻结/释放是否配对，撤单与收盘是否泄漏冻结
- [ ] 异常路径是否被吞掉或泄露到 UI 线程
- [ ] 是否有未标注的 AI 生成代码
```
