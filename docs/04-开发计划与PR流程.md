## 3. PR 流程（规格第 11 节强制要求）

### 3.1 硬性规则
1. 任何代码变更（无论人写还是 AI 生成）都必须通过 Pull Request 合入主分支，且至少一名队友 review 后才能 merge；
2. AI 生成的代码/算法/测试必须在 PR 描述中显式标注 `[AI-Generated]`；
3. review 不是走过场：必须对线程安全、异常处理、撮合逻辑正确性留下实质评论；
4. 最终文档需附仓库链接与已关闭 PR 讨论，演示时会被抽查。

### 3.2 本地（尚无远端时）如何落地

远端仓库需要你的 GitHub/Gitee 账号后才能创建，在此之前先在本地把流程跑成可查记录：

```bash
cd G:/项目/java-stock-auction

# 1) 每个功能开一个分支
git checkout -b feature/matching-engine

# 2) 开发并提交（小步提交，便于 review）
git add -A && git commit -m "feat(engine): 价格-时间优先撮合与部分成交"

# 3) 合入主干时保留合并记录（不要 fast-forward，保留可追溯的合并点）
git checkout main
git merge --no-ff feature/matching-engine -m "merge: 撮合引擎（reviewer: <队友名>）"

# 4) 远端就绪后推送并开 PR
git remote add origin <你的仓库地址>
git push -u origin main
git push origin feature/matching-engine

# 5) 需要留档时把讨论导出到仓库，供抽查
mkdir -p docs/pr-reviews && echo "<PR 链接与讨论摘要>" > docs/pr-reviews/PR-001-matching-engine.md
```

### 3.3 PR 描述模板（可直接复制）

```markdown
## 变更内容
- 一句话说明本 PR 做了什么

## 关联评分项
- [ ] 核心：撮合 / 多标的 / 账户 / GUI / CSV / 异常校验
- [ ] 进阶：多线程 / 市价单 / LLM / 撤单

## AI 参与标注
- [AI-Generated] 哪些文件/方法由 AI 生成或大幅改写（必填，没有则写“无”）

## 线程安全说明
- 共享状态、加锁范围、锁顺序；是否有锁外副作用

## 验证证据
- `mvnw.cmd test` 结果（Tests run / Failures / Errors）
- 手工验证步骤与真实输出片段

## Reviewer 检查点
- [ ] 撮合是否可能出现订单簿交叉（bestBid ≥ bestAsk）
- [ ] 冻结/释放是否配对，撤单与收盘是否泄漏冻结
- [ ] 异常路径是否被吞掉或泄露到 UI 线程
- [ ] 是否有未标注的 AI 生成代码
```
