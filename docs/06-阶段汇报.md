## 四、关键技术决策（可答辩）

1. **单锁撮合**：校验、冻结、撮合、记账、改簿全部在同一临界区完成，等价于规格要求的
   `submitOrder()` 必须 synchronized，保证状态变更完全串行化、正确性可证明。
   代价是吞吐上限——已识别，后续可按标的做分段锁优化。
2. **下单即冻结**：只做"下单时检查余额"会导致同一 agent 并发挂单时双花（账户变负）；
   本系统受理时冻结资金/持仓，成交按实际价结算、撤单与收盘回退，并在买单吃簿时以
   "该单剩余冻结 + 可用现金"为上限，使负现金在数学上不可能出现。
3. **成交价取被动方价格**：与真实交易所一致，使"价格发现"具有可追溯的因果链
   （谁先挂单谁定价，主动方获得价格改善）。
4. **订单簿用 TreeMap + FIFO 队列**：语义上等价于规格建议的两个优先队列，
   但撤单复杂度从 O(n) 降到 O(log n)，无需惰性删除标记。
5. **行情广播在锁外 + 监听者异常隔离**：慢的 GUI 渲染或 CSV 落盘不会拖住撮合，
   写错的监听者不会使整个市场停摆。

## 六、过程中发现的三处规格缺口及处理

这三处若不处理，系统会"代码全绿但跑不起来"，已补齐并写入项目文档与项目记忆：

| 缺口 | 后果 | 处理方式 |
| --- | --- | --- |
| 规格只定义初始资金，未定义初始持仓 | 所有人只有现金、无股票可卖，卖出必然失败，**首笔成交永远无法产生** | 新增配置项"初始持仓"，并为做市 agent 发放底仓 |
| 行情快照只在订单受理后推送 | agent 依赖行情决策，形成"没人下单→没行情→没人下单"的**死锁** | 开盘先推一次行情；并强制 agent 订阅行情总线 |
| 收益率以"初始资金"为分母 | 注入的持仓成本被误算成收益（实测做市 agent 虚增 +339%） | 收益率基准改为"初始权益 = 初始资金 + 初始持仓成本" |

> 前两处是单元测试全绿时依然存在的故障，只有端到端集成测试能暴露，因此项目保留了真起线程的集成测试。
